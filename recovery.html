BODH OS · SCHOOL LAB GUIDE

Recover without losing the work.

Start with diagnostics. Back up important files before changing the system.

These procedures require the correct computer, disk and backup destination. First practise on a disposable VM. Never guess a disk name or treat a failed operation as a successful repair.

If the desktop still opens

  1. Open Bodh Rescue and choose Diagnose boot and storage. This is a read only check. Save the output for the administrator.
  2. For a slow desktop, select Reduced in Bodh Settings. If the layout is damaged, use Reset Bodh desktop. It backs up the desktop configuration and keeps project files.
  3. For a coding project, use Student files to create and verify a backup on a separate mounted drive or school share.

If the installed system cannot start

  1. Boot the verified Bodh ISO into its live desktop. Live session files are temporary.
  2. Open Rescue diagnostics. Identify the installed system disk, filesystem and firmware mode.
  3. Have the administrator mount the installed root filesystem. For UEFI repair, mount that installation's EFI partition at its boot/efi directory. Boot the live ISO in the same firmware mode as the installation.
  4. Back up the installed users' important files to a different mounted destination before attempting repair.

Project backup and restore

Student files backups contain a project archive and integrity manifest. Use Verify an existing backup first. Restore creates a new folder and leaves the original project in place. Incomplete folders and damaged archives are rejected.

Rescue backups contain copied files on Linux filesystems, or a files.tar archive on portable filesystems. Keep the backup folder intact. An administrator must copy or extract these into a new folder and check the recovered files before putting them back. Rescue does not currently provide a general file restore wizard.

A mounted school share or USB drive must have enough free space and remain connected. If a copy is interrupted, read the failure log, reconnect or free space, then create a new backup. Keep earlier verified copies.

Boot repair

This release repairs x86_64 BIOS and UEFI installations. ARM64 boot repair is disabled because its boot targets need separate implementation and testing.

Boot repair reinstalls GRUB. It does not recover deleted documents or fix every possible disk failure. In Rescue, select the mounted installed root and its correct whole disk. Review the BIOS or UEFI mode and explicit confirmation before authorizing repair. If the root, disk or EFI mount is wrong, stop and correct the selection.

After successful repair, restart without the ISO. Confirm login and open a saved student project. If repair fails, keep its diagnostic output. Do not format or reinstall over the only copy of student work.

Undo a failed update

Timeshift must have been configured and a valid snapshot created before the failure. Open Configure or restore snapshots from Bodh Settings, or the matching Timeshift recovery tool from a live environment. Select the intended snapshot and installed target, then review its restore options.

Back up student files separately first. System snapshots are not a substitute for project backups. After restoration, restart and check the desktop, network, package state and saved projects.

Authorization and failure messages

If a package index cannot be refreshed, the update stops before upgrading packages. Check the connection and mirror, resolve the reported error and retry. Do not treat a failed refresh as a completed update.

Canceling an administrator prompt leaves the operation unfinished. A failed snapshot blocks protected package changes. A checksum failure means the backup is not verified. Record the message and resolve the cause before retrying.
